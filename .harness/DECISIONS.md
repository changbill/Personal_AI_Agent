| 2026-09-13 | 한국 주요 지명의 좌표 표를 이 저장소가 소유하고, Geocoding API는 폴백으로만 쓴다 | Open-Meteo Geocoding의 색인은 로마자여서 `language=ko`를 줘도 한국어 이름으로 검색되지 않는다. 실측에서 "서울"과 "제주"는 결과가 0건이었고, "대전"은 전라남도의 동명 지역이, "부산"은 경상북도의 동명 지역이 1순위로 나왔다. 결과 0건보다 이쪽이 더 나쁘다 — 모델이 엉뚱한 지역의 날씨를 사실처럼 답한다. 지명→좌표는 규칙으로 판정 가능하므로 LLM에도 외부 서비스에도 묻지 않는다. 표에 있으면 네트워크 왕복도 하나 줄어든다. 좌표는 로마자 이름으로 Geocoding을 조회해 행정구역을 확인한 값이라 예보 격자는 API가 골랐을 지점과 같다. 기상청 단기예보 API는 키 발급과 격자 좌표 변환이 필요하고 해외 도시를 다루지 못해 제외했다. |

| 2026-09-13 | 주입하는 오늘 날짜를 `AGENT_TIMEZONE` 기준으로 계산한다. `date.today()`를 쓰지 않는다 | `date.today()`는 OS 로컬 시간대를 따르는데 `AGENT_TIMEZONE`은 프롬프트 문자열로만 쓰이고 있었다. 호스트가 UTC면 한국 시간 자정부터 오전 9시까지 날짜가 하루 밀린다. 실측으로 같은 순간에 `Asia/Seoul`은 2026-09-13, `UTC`는 2026-09-12로 갈렸다. 시계는 생성자 인자로 주입받게 해 테스트가 결정론적으로 남는다. |
| 2026-09-13 | `get_current_time` Tool을 General Agent에만 등록하고, Schedule·Search는 프롬프트 주입을 유지한다 | 일정·날씨 요청은 날짜가 항상 필요하므로 주입이 맞다. Tool로 받으면 조회 한 번에 모델 왕복이 둘이 되어 4.2 tok/s 환경에서 약 15초가 더 붙고, 모델이 시간 Tool을 건너뛰면 날짜를 지어낸다. 반대로 General Agent는 날짜 맥락이 전혀 없어 "오늘 며칠이야"에 답할 수 없었고, 대화 대부분은 날짜가 필요 없으므로 상시 주입은 Context 낭비다. |
| 2026-09-13 | 시각 소스는 timeapi.io를 주 소스로 쓰고 로컬 시계를 폴백으로 둔다 | 키 없이 쓸 수 있는 유일한 동작 후보였다. `worldtimeapi.org`는 서비스가 종료되어 연결이 리셋되고, `timeapi.world`는 조사한 경로에서 404였다. 무료 한도가 문서화되어 있지 않아 언젠가 막힐 수 있으므로, 네트워크 실패·응답 손상·한도 초과가 모두 로컬 시계로 떨어지게 했다. 시간 조회가 응답 실패의 원인이 되면 안 된다. 어느 소스를 썼는지는 로그에 남긴다. |
| 2026-09-13 | `tzdata`를 의존성에 추가하고 `AGENT_TIMEZONE`을 기동 시점에 검증한다 | Windows에는 IANA 시간대 DB가 없어 `zoneinfo`가 `ZoneInfoNotFoundError`로 실패한다. 개발 머신과 미니PC의 동작을 같게 하려면 패키지로 고정해야 한다. 시간대 오타를 기동 시점에 잡지 않으면 잘못된 날짜가 프롬프트에 조용히 들어간다. |
| 2026-09-12 | 일정 데이터는 자체 저장소를 두지 않고 Google Calendar를 유일한 출처로 삼는다 | 사용자가 이미 Google Calendar로 일정을 관리한다. 자체 일정 테이블을 두면 사용자의 실제 캘린더와 두 벌이 되어 어긋난다. 부수 효과로 "PostgreSQL은 Long-term Memory 전용" DB 정책을 고치지 않아도 된다. Calendar API는 쿼터 기반 무료여서 비용 제약에도 맞는다. |
| 2026-09-12 | 캘린더 연동은 커뮤니티 MCP 서버 `@cocal/google-calendar-mcp` v2.6.3을 Docker로 빌드해 streamable HTTP로 붙인다 | 공식 Google Workspace MCP는 2026년 5월부터 출시된 **원격** 서버이고 커넥터 사용에 유료 플랜을 요구한다. 상시 로컬 운영 개인 비서에 원격 유료 의존을 넣는 구조는 이 프로젝트의 비용·자립 제약에 정면으로 걸린다. 미니PC에 Node.js를 설치하지 않으려고 Docker를 택했고, 공개 이미지가 없어 git 태그에서 빌드한다. 태그를 고정하는 이유는 모델 태그와 같다 — 대상이 바뀌면 Tool 선택 정확도 측정이 무의미해진다. |
| 2026-09-12 | MCP Tool을 그대로 노출하지 않고 자체 `@tool` 래퍼로 감싼다 | MCP 서버가 Tool의 이름·Description·입력 스키마를 소유하므로, 그대로 쓰면 LLM이 보는 설명이 편집 불가능한 영어 한 줄(`Create a new calendar event.` 등)이 되고 비호출 조건을 붙일 수 없다. 소형 로컬 모델에서 Description은 주석이 아니라 Tool 선택 로직이다. 래퍼가 Description과 Tool 이름을 소유하면 `DOMAIN.md` 설계와 코드가 일치하고, 인자 검증도 외부 호출 전에 Application이 수행할 수 있다. |
| 2026-09-12 | Schedule Agent에 Tool 4개(조회·생성·수정·삭제)를 모두 등록한다. MCP 서버의 나머지 8개는 차단한다 | 사용자가 일정 관리 기능 전체를 원했다. 12개를 그대로 노출하면 2B 모델의 오선택이 급증하므로 `tool_filters`와 Application 허용 목록으로 4개만 남긴다. 4개에서의 오선택률은 Phase 8 평가로 측정한다. |

| 2026-09-12 | 캘린더 서버 장애를 요청 실패로 만들지 않는다. Tool 0개로 격리하고 Agent가 연결 불가를 말한다 | 캘린더가 없어도 나머지 대화는 동작해야 한다. 또한 OAuth 자격증명이 아직 없는 상태에서도 API가 뜨고 다른 Phase 작업을 계속할 수 있어야 한다. 동작하지 않는 Tool을 등록해 두면 모델이 가져오지 않은 일정을 사실처럼 말한다. |
| 2026-09-12 | 날씨 Tool의 제공자로 Open-Meteo를 쓰고, `search_web`·`search_place`는 Phase 3-B로 미룬다 | Open-Meteo forecast API는 비상업적 사용에 API key가 필요 없어 계정·카드 없이 외부 정보 Tool 경로를 증명할 수 있다. 반면 Brave Search 무료 tier는 2026년 2월에 폐지되어 카드 등록 후 월 $5 크레딧제로 바뀌었고, Tavily·Firecrawl·SerpApi는 계정과 낮은 월 쿼터를 요구하며, SearXNG 자체 호스팅은 미니PC RAM·CPU를 상시 점유한다. 무료 제공자 판단이 끝나기 전에 Tool을 붙이지 않는다. |
| 2026-09-12 | 오늘 날짜·요일·시간대를 코드가 계산해 system prompt에 주입하고, MCP의 `get-current-time` Tool은 등록하지 않는다 | 규칙으로 판정 가능한 것을 LLM에 묻지 않는다는 정책을 따른다. 시간 조회 Tool을 등록하면 일정 요청마다 LLM 왕복이 한 번 더 늘어 CPU 추론 지연이 배가된다. |

| 2026-09-10 | `CLAUDE.md`와 `AGENTS.md`를 전문 복제로 유지하고 `scripts/check_docs_sync.sh`로 검증한다 | Claude Code는 CLAUDE.md를, Codex는 AGENTS.md를 읽는다. 한쪽만 두고 import하는 방식은 평문으로 읽는 도구가 내용을 못 본다. 실제로 이미 drift가 발생했었다 — 이전 Java 프로젝트에서 AGENTS.md가 DOMAIN.md 관련 항목 4개를 조용히 잃은 상태였다. 사람의 규율에만 맡기면 반복되므로 기계적 검사를 붙인다. |
| 2026-09-10 | 별도 `docs/api/openapi.yaml`을 두지 않는다 | FastAPI가 Pydantic 스키마와 라우터에서 OpenAPI를 자동 생성한다. 별도 스펙 파일을 두면 코드와 두 벌이 되어 어긋난다. 코드를 계약의 단일 원본으로 삼는다. |
| 2026-09-10 | 패키지·가상환경 관리를 `uv`로 고정한다 | `uv.lock`으로 재현성이 보장되고, 미니PC에서의 Docker 빌드 시간이 짧아진다. 비용 최소화가 최우선 제약인 프로젝트에서 빌드·재빌드 비용도 운영 비용이다. |
| 2026-09-10 | 테스트를 `unit` / `integration` / `llm` 세 마커로 분리하고, 기본 검증은 `unit`만 실행한다 | LLM 호출 테스트는 느리고 비결정적이며 Ollama 기동을 요구한다. 이것이 기본 검증에 섞이면 개발 루프가 느려지고, Ollama가 없는 환경에서 스위트 전체가 깨진다. |
| 2026-09-10 | 평가(`tests/evaluation/`)를 일반 테스트 스위트에서 분리한다 | 평가는 pass/fail이 아니라 지표 측정이다. 정확도가 100%가 아니라고 CI가 실패하면 평가를 돌리지 않게 되고, 그러면 "성능이 개선됐다"는 주장을 검증할 수단이 사라진다. |
| 2026-09-10 | 개발 머신(Windows 데스크톱)에 Ollama를 설치해 벤치마크하지 않는다 | 개발 머신에는 GTX 1660 SUPER 6GB가 있고 배포 대상 미니PC에는 GPU가 없을 가능성이 높다. 여기서 잰 응답 속도와 실행 가능 모델 크기는 미니PC로 이전되지 않으므로, 측정해도 잘못된 결론만 남는다. 하드웨어 무관 품질 지표만 이전 가능하다. |
| 2026-09-10 | 모델은 `latest`가 아니라 명시적 태그로 고정한다 | `qwen3.5:latest`는 현재 9b를 가리킨다. 태그가 가리키는 대상이 바뀌면 이전 평가 결과와 비교가 불가능해진다. |
| 2026-09-10 | thinking 모드를 끄는 것을 기본으로 한다 | Ollama에서 thinking 지원 모델은 옵션 미지정 시 자동 활성화된다. Agent 라우팅처럼 짧은 판단만 필요한 호출에서 CoT를 생성하면 CPU 추론 지연이 배로 늘어, 비용·응답시간 제약에 정면으로 걸린다. **적용 경로는 Phase 1에서 실측 검증 예정.** |

| 2026-09-10 | `main`에 직접 커밋하지 않고 `phase{번호}/{설명}` 브랜치를 쓴다. `develop`은 두지 않는다 | 이전 Java 프로젝트의 Jira 티켓 브랜치 규칙은 이 저장소에 티켓 시스템이 없어 그대로 쓸 수 없다. 1인 개인 프로젝트에 `develop`까지 두면 관리 비용만 늘어난다. Phase 단위가 이 프로젝트의 실제 작업 단위다. |
